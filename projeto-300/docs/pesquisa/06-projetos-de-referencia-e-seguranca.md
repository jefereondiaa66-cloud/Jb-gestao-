# Levantamento de projetos open-source semelhantes (assistentes estilo JARVIS, agentes de desktop, pipelines de voz, memória) e lições de segurança (prompt injection, envenenamento de ferramentas MCP, OWASP), visando reaproveitar componentes no "300"

> Pesquisa feita em 02/11/2026 por agentes com busca na web, conferida por um verificador adversarial independente. Itens marcados como 'não verificado' não puderam ser confirmados na fonte oficial (alguns sites estavam fora da rede do ambiente de pesquisa).

## Resumo

Nenhum projeto open-source reúne o que o "300" precisa: app de desktop Windows em Node/TS, wake word local em pt-BR, conversa com interrupção (barge-in), controle do computador com permissões e memória longa. Os mais próximos têm lacunas. OpenClaw (MIT, ~394k estrelas, TS) é centrado em canais de chat, roda ferramentas no host por padrão e tem enorme volume de advisories. Goose (Apache-2.0, desktop Electron 43 + núcleo Rust) não tem voz e vem em modo Autônomo por padrão. UI-TARS-desktop (Apache-2.0, Electron 34) tem permissões fracas e SDK parado desde 06/2025. Leon (MIT) ainda é "2.0 Developer Preview" e depende de bridges Python. Não achei nenhum assistente Electron open-source maduro com wake word local e pt-BR: IRIS-AI tem núcleo fechado e wake word só no plano "Pro"; o projeto de akshayaggarwal99 é só para Mac e funciona apertando uma tecla. Conclusão: construir um núcleo próprio e reaproveitar PADRÕES (pipeline por estágios/eventos do Home Assistant Assist, quadros de interrupção do Pipecat, memória com proveniência e "taint" do OpenClaw, extração de fatos do Mem0, motor de permissões deny>ask>allow do Claude Code, execpolicy do Codex, executores COM/UIA do UFO2) e COMPONENTES com licença permissiva (sherpa-onnx, Silero VAD, modelos de features do openWakeWord, Smart Turn v3.2, sandbox-runtime, MCP SDK v2).

Achados que mudam a stack:
(1) O MCP TS SDK v2 já é a linha estável: @modelcontextprotocol/client 2.4.0, de 23/10/2026, com a spec 2026-07-28, que é stateless. O @modelcontextprotocol/sdk 1.32.2 é v1.
(2) @nut-tree-fork/nut-js 4.2.6 está sem publicação desde 15/03/2025. O nut.js oficial tirou os pacotes públicos do npm; os binários prontos agora são pagos.
(3) keytar está sem release desde 02/2022. Usar safeStorage (DPAPI) ou @napi-rs/keyring 2.1.2, que tem builds win32.
(4) Modelos acessíveis pelo GitHub (o container de build alcança): as vozes Piper pt_BR (faber, edresson, cadu, jeff) e o Kokoro multi-lang estão nos releases do k2-fsa/sherpa-onnx (HTTP 200 verificado). O melspectrogram.onnx e o embedding_model.onnx do openWakeWord estão no release v0.5.1 (HTTP 200).
(5) Exigem mirror manual porque ficam no Hugging Face: Smart Turn, o turn-detector do LiveKit e o UI-TARS. Os modelos KWS do sherpa-onnx cobrem só inglês/chinês, sem português.

Segurança: o padrão de incidentes em 2025-2026 é injeção indireta (web, e-mail, issues, descrições de ferramentas MCP) somada a ferramentas amplas e saída de rede livre. Exemplos: EchoLeak CVE-2025-32711, GitHub MCP, OpenHands "ZombAI", Claude Desktop "PromptJacking", postmark-mcp malicioso, sobrescrita de config levando a RCE em Cursor/Copilot/Roo. Os ataques adaptativos ainda passam: Anthropic reporta 1,4% a 2,4% de sucesso com as salvaguardas atuais. As defesas que funcionam são estruturais: privilégio mínimo, mediação completa fora do LLM, sandbox de SO, lista de domínios permitidos, confirmação por ação e memória com proveniência.

Limitações desta pesquisa: a API do GitHub estava bloqueada, então as estrelas vêm das páginas github.com em 02/11/2026 (valores aproximados) e as datas de último commit vêm de clones rasos. O orçamento de WebSearch esgotou. Os domínios home-assistant.io, docs.pipecat.ai, genai.owasp.org, arxiv.org, openai.com, ai.meta.com, simonwillison.net e electronjs.org não resolvem nesta sessão. Usei os repositórios GitHub equivalentes quando possível e marquei o resto como "não verificado".

## Recomendação

Construir núcleo próprio (Electron 45 + TS + Node 22), sem adotar nenhum framework completo. Reaproveitar PADRÕES e COMPONENTES de licença permissiva:
(a) Pipeline de voz como máquina de estados com o contrato de eventos do Home Assistant Assist e quadros de sistema estilo Pipecat para barge-in. Usar sherpa-onnx-node (Apache-2.0) para VAD/STT/TTS, Silero VAD (MIT) e Smart Turn v3.2 (BSD-2, via onnxruntime-node) espelhado em release próprio no GitHub.
(b) Wake word 'trezentos': classificador próprio sobre os modelos de features do openWakeWord (melspectrogram.onnx + embedding_model.onnx, release v0.5.1 no GitHub), treinado com amostras sintéticas das vozes Piper pt_BR. Os modelos pré-treinados do openWakeWord são CC BY-NC-SA e não servem.
(c) MCP via @modelcontextprotocol/client 2.4.0 (v2 estável, spec 2026-07-28), e não o @modelcontextprotocol/sdk 1.32.2.
(d) Motor de permissões próprio: deny→ask→allow com primeiro match (Claude Code), regras de comando no estilo prefix_rule com testes match/not_match (Codex execpolicy), caminhos protegidos, confirmação por tool_use e revisor fail-closed.
(e) Memória no better-sqlite3-multiple-ciphers + sqlite-vec, com proveniência e taint por turno (OpenClaw) e extração ADD-only (Mem0) reimplementada, sem depender do pacote mem0ai.
(f) Controle do Windows priorizando APIs/COM/UIA (padrão UFO2) e input sintético só como fallback, com o mínimo de ferramentas abertas: nada de shell genérico; se houver, só dentro do @anthropic-ai/sandbox-runtime.

**Alternativas:**

- Se for aceitável um sidecar Python no PC (contraria a meta): Pipecat (BSD-2) como servidor local de voz com transporte Local/SmallWebRTC e o Electron como cliente via @pipecat-ai/client-js 1.16.0. Ganha Smart Turn e estratégias de turno prontas.
- Se quiser framework de voz em Node: @livekit/agents 1.9.5 (Apache-2.0) com livekit-server local. Custos: servidor de mídia extra, openai ^6 duplicado, módulos nativos e turn detector sob LiveKit Model License hospedado no HF.
- Para acelerar a UI e o gerenciamento de MCP/provedores: estudar ou forkar trechos do app Electron do Goose (Apache-2.0), trocando o default Autônomo por Manual e o revisor fail-open por fail-closed.
- Para o operador de desktop por visão: o código do operator nut-js do UI-TARS-desktop (Apache-2.0) como referência, ou o computer_toolset_20260801 da Claude com executor próprio e confirmação antes de cada tool_use.
- Para a memória, se reimplementar for caro: mem0ai 3.3.1 em modo OSS com store SQLite, aceitando openai ^4 e better-sqlite3 ^12 como dependências e revisando o rebuild nativo no Electron.

**Justificativa:** O levantamento mostra três coisas. (1) Nenhum projeto cobre Windows + Node + pt-BR + wake word local + barge-in + controle do PC com permissões. Os candidatos mais próximos têm problemas estruturais: OpenClaw roda ferramentas no host por padrão e tem superfície enorme; Goose não tem voz e é autônomo por padrão; UI-TARS está com Electron 34 e SDK parado; Leon está em preview e usa Python; 01 é AGPL e está abandonado; Rhasspy foi arquivado; Willow exige ESP32. (2) Os componentes que valem a pena são pequenos, permissivos e acessíveis a partir do GitHub, o que respeita a restrição do container de build: sherpa-onnx e seus modelos pt_BR em releases, modelos de features do openWakeWord, Silero VAD e sandbox-runtime. (3) A segurança só funciona como propriedade estrutural. Classificadores e detecção por padrões (Goose, Anthropic) reduzem o sucesso de ataque para algo em torno de 1% a 2,4%, mas ataques adaptativos ainda passam. Por isso o desenho precisa ter: escopo mínimo de ferramentas (OWASP LLM06), mediação completa no código, proveniência na memória, allowlist de rede, sandbox de SO e confirmação humana por ação de risco. Copiar padrões bem documentados (contrato de eventos do HA, quadros do Pipecat, proveniência do OpenClaw, precedência de regras do Claude Code) reduz risco de projeto sem herdar dependências Python nem licenças restritivas.

### Prós e contras

**OpenClaw (openclaw/openclaw)**

- ✅ É a referência mais próxima em TS para um assistente pessoal 'always-on', com gateway, canais, cron, memória, nós de voz e apps móveis
- ✅ A arquitetura de memória é a melhor encontrada. Cada entrada tem proveniência como coluna SQLite que o modelo não consegue escrever (owner/agent/untrusted/system). Depois de um resultado de rede, o resto do turno fica marcado (taint). Sessões cron/heartbeat/subagente não geram memória durável. Há prevenção de loop de recall, um único escritor (passe de consolidação 'dreaming') e um índice SQLite com arquivos editáveis
- ✅ O guia de prompt injection é muito prático: agente 'leitor' sem ferramentas para resumir conteúdo não confiável, marcadores <<<EXTERNAL_UNTRUSTED_CONTENT>>>, remoção de tokens especiais de chat-template, strictInlineEval para interpretadores e heredoc sempre com aprovação
- ✅ Wake words ficam numa lista global no gateway (até 32 gatilhos, 64 unidades UTF-16 cada) sincronizada com os nós. É um bom modelo para o futuro app Android como 'satélite'
- ✅ Pareamento obrigatório de remetentes desconhecidos em canais de DM
- ⚠️ Ferramentas rodam no host por padrão; o sandbox é opt-in
- ⚠️ O SECURITY.md declara prompt injection 'fora de escopo' quando não há bypass de política. A defesa é responsabilidade de quem configura
- ⚠️ Superfície gigante (20+ canais, plugins, skills) e volume alto de advisories
- ⚠️ Foco em chat por apps de mensagens, não em voz contínua no PC. O voice wake do macOS usa reconhecimento do sistema e exige macOS 26
- ⚠️ Requer Node 24+/26, diferente do Node 22 da stack
- Fontes: https://github.com/openclaw/openclaw, https://github.com/openclaw/openclaw/blob/HEAD/docs/concepts/memory-architecture.md, https://github.com/openclaw/openclaw/blob/HEAD/docs/gateway/security/prompt-injection.md, https://github.com/openclaw/openclaw/blob/HEAD/docs/nodes/voicewake.md, https://github.com/openclaw/openclaw/blob/HEAD/SECURITY.md, https://github.com/openclaw/openclaw/security/advisories, https://github.com/openclaw/clawhub

**Goose (block/goose, agora no Agentic AI Foundation / Linux Foundation)**

- ✅ Prova que Electron + MCP + vários provedores funciona em desktop em produção
- ✅ Quatro modos de permissão: Autonomous / Manual Approval / Smart Approval / Chat Only, com permissões por ferramenta
- ✅ 'Adversary mode': um revisor independente com regras em linguagem natural (~/.config/goose/adversary.md) vê a tarefa original, as mensagens recentes e a chamada de ferramenta, e devolve ALLOW/BLOCK
- ✅ Detecção de prompt injection por padrões (crates/goose/src/security/patterns.rs), com ML opcional e decisões registradas com finding ID
- ✅ Allowlist de extensões MCP por comando de instalação (GOOSE_ALLOWLIST)
- ⚠️ Modo Autônomo é o PADRÃO, um anti-padrão para nós
- ⚠️ O adversary mode é fail-open (se o revisor falha, a chamada passa); nós precisamos de fail-closed
- ⚠️ Por padrão o adversary só revisa a ferramenta 'shell'

## Notas de implementação

- PADRÃO RECORRENTE 1 (pipeline por estágios). wake_word → VAD → STT (streaming) → fim de turno → LLM (streaming) → TTS (streaming por frase) → playback. Emitir eventos no formato do HA: run-start, wake_word-start/end, stt-start, stt-vad-start/end, stt-end, intent-start, intent-progress {chat_log_delta, tts_start_streaming}, intent-end, tts-start/end, run-end, error {code}. Reusar os códigos: wake-word-timeout, stt-no-text-recognized, stt-stream-failed, intent-failed, tts-failed. Isso facilita UI, testes e auditoria (fonte: https://github.com/home-assistant/developers.home-assistant/blob/HEAD/docs/voice/pipelines/index.md).
- PADRÃO RECORRENTE 2 (barge-in no estilo Pipecat). Separar eventos de sistema (Interruption, UserStartedSpeaking, Cancel), que furam filas, dos eventos de dados, que seguem em ordem. Quando o VAD detectar fala com o TTS tocando: (1) parar o áudio na hora; (2) abortar o stream do LLM (AbortController); (3) esvaziar a fila de TTS; (4) gravar no histórico só o texto que de fato foi falado. O item 4 é prática de Realtime/LiveKit, não verificada nesta sessão. Ativar o AEC do getUserMedia (echoCancellation) no renderer para o próprio TTS não disparar interrupção (não verificado no Electron 45).
- PADRÃO RECORRENTE 3 (fim de turno). Usar Silero VAD para início e fim de fala e Smart Turn v3.2 (BSD-2, ~8 MB int8, entrada 16 kHz até 8 s, ~10–65 ms em CPU, inclui português) só após silêncio, sobre o turno inteiro. Os pesos ficam no Hugging Face (pipecat-ai), que o container de build não alcança: espelhar o .onnx num release do GitHub do próprio projeto, com SHA-256 fixado, ou baixar no PC do usuário no primeiro uso. O turn detector do LiveKit (livekit/turn-detector no HF, LiveKit Model License) tem o mesmo problema e licença pior.
- PADRÃO RECORRENTE 4 (comandos determinísticos antes do LLM). OVOS (Padatious/Adapt → persona LLM) e HA ('prefer handling commands locally') casam intents simples localmente (hora, volume, abrir app) antes de chamar o modelo. Isso corta latência e custo e reduz a superfície de injeção.
- PADRÃO RECORRENTE 5 (satélites). HA/Wyoming, Willow, 01 e os nós do OpenClaw usam dispositivo fino (mic, wake word e alto-falante) mais cérebro central. Para o Android futuro: o app vira satélite do PC ou funciona sozinho. Se for satélite, NÃO copiar o Wyoming 'sem autenticação nem criptografia por design': usar TLS + pareamento por código (como o 'pairing approve' do OpenClaw). Lista de wake words única no núcleo, sincronizada aos nós (OpenClaw: até 32 gatilhos, 64 unidades UTF-16 cada).
- MODELOS ACESSÍVEIS PELO GITHUB (verificado HTTP 200 em 02/11/2026). Em https://github.com/k2-fsa/sherpa-onnx/releases/download/tts-models/: vits-piper-pt_BR-faber-medium.tar.bz2, vits-piper-pt_BR-edresson-low.tar.bz2, vits-piper-pt_BR-cadu-medium.tar.bz2, vits-piper-pt_BR-jeff-medium.tar.bz2, kokoro-multi-lang-v1_0.tar.bz2, kokoro-int8-multi-lang-v1_1.tar.bz2. Em https://github.com/dscripka/openWakeWord/releases/download/v0.5.1/: melspectrogram.onnx e embedding_model.onnx. O release kws-models do sherpa-onnx só tem gigaspeech (inglês), wenetspeech (chinês) e zh-en-3M-2025-12-20; não há KWS em português, o que reforça o classificador próprio para 'trezentos'.
- WAKE WORD 'trezentos'. O openWakeWord treina modelos com 100% de fala sintética sobre um extrator congelado (Apache-2.0); os modelos pré-treinados são CC BY-NC-SA 4.0 e não podem ir num app distribuível. Plano: na máquina de desenvolvimento (Python só em dev-time), gerar milhares de 'trezentos' com as vozes Piper pt_BR variando velocidade e ruído, mais negativos ('trezentas', 'três', 'trinta', 'treze', TV/rádio). Opcional: 'custom verifier' com a voz do dono (README do openWakeWord), que reduz falsos positivos mas piora para outras vozes. Meta de referência do openWakeWord: menos de 0,5 falso aceite por hora e menos de 5% de falso rejeite.
- MCP. Trocar @modelcontextprotocol/sdk 1.32.2 (v1) por @modelcontextprotocol/client 2.4.0 (Apache-2.0, v2 estável, spec 2026-07-28: stateless, sem initialize, server/discover, subscriptions/listen, MRTR no lugar de sampling/elicitation iniciados pelo servidor). Exige TypeScript com "types": ["node"]. Regras da spec: anotações de ferramenta são NÃO CONFIÁVEIS salvo de servidor confiável. Na instalação de servidor local, mostrar o comando exato sem truncar, avisar que roda com os privilégios do app e rodar com privilégios mínimos (fontes: https://www.npmjs.com/package/@modelcontextprotocol/client e https://github.com/modelcontextprotocol/modelcontextprotocol/blob/HEAD/docs/docs/2026-07-28/tutorials/security/security_best_practices.mdx).
- MCP / ENVENENAMENTO DE FERRAMENTAS (Invariant Labs). Três ataques a cobrir. Direct poisoning: a descrição da ferramenta 'add' manda ler ~/.ssh e mcp.json. Shadowing: um servidor malicioso altera o comportamento do send_email de outro servidor. Rug pull: a ferramenta muda na 2ª carga para exfiltrar mensagens do WhatsApp, escondendo o payload após muitos espaços. Controles: (1) pinning por hash de nome + descrição + schema de cada ferramenta, com nova aprovação se mudar; (2) mostrar a descrição completa na aprovação, normalizando espaços e caracteres invisíveis (tags Unicode, zero-width); (3) namespacing por servidor, com proibição de descrições que citem outras ferramentas e servidores; (4) allowlist de servidores (padrão GOOSE_ALLOWLIST), sem instalação 'one-click' de npm arbitrário (caso real: postmark-mcp malicioso em 09/2025 com BCC das mensagens; pacote MCP com reverse shell em 10/2025). O mcp-scan virou 'Snyk Agent Scan' (Python/uvx, saída experimental), útil só como auditoria offline. O repo mcp-injection-experiments não tem LICENSE: usar como referência, sem copiar código.
- MOTOR DE PERMISSÕES (copiar a semântica do Claude Code). Avaliar deny → ask → allow, primeiro match vence, e uma allow nunca abre exceção dentro de uma deny. Hooks e plugins não podem converter deny/ask em allow. Ações que nenhum modo auto-aprova: apagar fora de pastas de trabalho, enviar e-mail ou mensagem, pagar, aceitar termos, instalar software, mudar configuração do próprio 300. Lista de caminhos protegidos, adaptada ao Windows: %APPDATA%\300\, perfis de navegador, .ssh, .gitconfig, Startup, chaves Run do registro, PowerShell profile. Para comandos, usar prefix_rule com decision allow/prompt/forbidden e exemplos match/not_match validados ao carregar (Codex execpolicy) e host_executable para fixar caminhos absolutos. Lembrar: regra por texto de comando NÃO é fronteira; a fronteira é o sandbox.
- CONFIRMAÇÃO. Pedir confirmação ANTES DE CADA bloco tool_use, não uma vez por turno: a doc de computer use avisa que um turno pode encadear várias ações. A confirmação por voz deve repetir a ação concreta e o alvo (ex.: 'enviar e-mail para fulano@x com 2 anexos?'), com a opção de ver o detalhe na tela. Para ações de alto impacto, exigir confirmação na tela (clique ou PIN), porque um áudio tocando no PC (vídeo, página) pode imitar o dono (OWASP ASI09, exploração da confiança humano-agente). Evitar 'approval fatigue': o sandbox com allowlist reduziu em 84% os prompts internos da Anthropic.
- REVISOR / CLASSIFICADOR DE AÇÕES. Usar um juiz separado (ex.: claude-haiku-5-5 ou sonnet) que recebe só o pedido do usuário, as mensagens recentes do dono e a chamada proposta. NUNCA mostrar ao juiz os resultados de ferramentas: o Claude Code tira os tool results para o conteúdo hostil não manipular o juiz. FAIL-CLOSED, ao contrário do adversary mode do Goose, que é fail-open. A detecção por padrões estilo Goose (rm -rf, curl|sh, acesso a .ssh) serve só como camada extra.
- QUARENTENA DE CONTEÚDO NÃO CONFIÁVEL (dual-LLM / agente leitor). Web, e-mail, PDFs, OCR de tela e documentos passam primeiro por um agente 'leitor' SEM ferramentas, que devolve resumo ou dados estruturados. O agente principal recebe o conteúdo dentro de delimitadores com metadados de origem (estilo <<<EXTERNAL_UNTRUSTED_CONTENT … Source: External>>> do OpenClaw), com tokens especiais de chat-template removidos. Para tarefas com dados privados, preferir o desenho 'plan-then-execute' do CaMeL (Google DeepMind, arXiv 2503.18813; o repo Apache-2.0 é artefato de pesquisa sem manutenção): o plano sai só do pedido do dono e os dados não confiáveis não alteram o fluxo.
- REGRA PRÁTICA ('lethal trifecta' de Simon Willison, 06/2025, e 'Agents Rule of Two' da Meta, 10/2025; não verificados nesta sessão porque os domínios estão bloqueados). Nenhuma sessão deve ter ao mesmo tempo (A) entrada não confiável, (B) acesso a dados privados ou sistemas sensíveis e (C) capacidade de mudar estado ou comunicar para fora sem confirmação humana. Implementar como política: ler conteúdo de rede marca a sessão com taint até a próxima fala do dono. Com taint, ferramentas de envio, escrita fora do sandbox e navegação para domínios novos passam para 'ask' obrigatório.
- MEMÓRIA (padrões OpenClaw + Mem0). Tabela de memórias com colunas que o modelo não escreve: origin ∈ {owner, agent, untrusted, system}, session_kind ∈ {interactive, cron, heartbeat, subagent}, observed_at, supersedes_key, source_session_id. Regras: (1) cron e tarefas de fundo não criam memória durável; (2) conteúdo injetado por recall nunca é re-extraído, evitando loop; (3) depois de ferramenta de rede, o turno inteiro vira 'untrusted'; (4) um único escritor faz a consolidação em background para o 'núcleo' sempre carregado, com promoção só de origin=owner/agent; (5) 'esquecer' por sessão de origem. Extração no estilo Mem0 atual: um passe só, ADD-only, deduplicação por entidade, recuperação híbrida (sqlite-vec + FTS5 BM25 + entidades). Cifrar o banco com better-sqlite3-multiple-ciphers e guardar a chave via safeStorage. Isso cobre OWASP LLM08 e ASI06 (envenenamento de memória).
- CONTROLE DO WINDOWS (padrão UFO2). Ordem de preferência: (1) API ou integração nativa (Graph/Gmail APIs, COM do Office para Word/Excel/PowerPoint, shell:AppsFolder para abrir apps); (2) árvore UI Automation (clicar por AutomationId ou nome de controle, set_edit_text); (3) coordenadas a partir de screenshot só como fallback. Para UIA a partir do Node sem Python: PowerShell com System.Windows.Automation ou addon N-API próprio (não verificado; não achei pacote npm mantido). Sobre o @nut-tree-fork/nut-js 4.2.6: sem publicação desde 2025-03-15; @computer-use/nut-js 4.2.0 sem publicação desde 2025-01-09; o nut.js oficial removeu os pacotes públicos do npm e os binários prontos são por assinatura. Se usar, fixar versão, vendorizar e isolar atrás de interface própria.
- NAVEGADOR. Perfil dedicado do Playwright (playwright-core) e NUNCA o perfil principal do usuário: o agenticSeek importa a sessão do navegador e expõe senhas e cookies. Allowlist de domínios por tarefa; senhas digitadas via placeholder e nunca no contexto (o browser-use avisa que snapshots e histórico guardam segredos em claro); downloads em pasta de quarentena. Em TS, o Stagehand 4.3.0 (MIT, Chrome local) é opção para act/observe/extract. O npm 'browser-use' 0.9.0 é port não oficial: evitar.
- SANDBOX DE EXECUÇÃO. Se houver ferramenta de script ou comando: @anthropic-ai/sandbox-runtime 0.0.81 (Apache-2.0). No Windows (alpha) exige `npx @anthropic-ai/sandbox-runtime windows-install` elevado uma vez, cria a conta srt-sandbox e usa cerca de saída WFP, com escrita negada por padrão (allowWrite) e rede default-deny (allowedDomains). Limitação: curl.exe, Invoke-WebRequest, .NET HttpClient e winget (Schannel) não fazem HTTPS dentro dele. Alternativa: não oferecer shell genérico (OWASP LLM06 item 3: evitar extensões abertas como 'rodar comando' ou 'buscar URL'). O Codex também tem sandbox Windows nativo (codex-rs/windows-sandbox-rs) como referência.
- HARDENING ELECTRON. contextIsolation: true, sandbox: true, nodeIntegration: false, sem <webview> (advisory de 2026 GHSA-9qh4-3jw8-366w: webview reativando Node em Web Workers), sem abrir janelas a partir de documento sandboxed (GHSA-gr2m-v5gq-v685). Validar o remetente em todo IPC; CSP estrita; shell.openExternal só com allowlist (GHSA-997q-gvvc-jwmx: origem errada no pedido de openExternal). Fuses via @electron/fuses 2.1.3: RunAsNode off, EnableNodeOptionsEnvironmentVariable off, EnableNodeCliInspectArguments off, EnableEmbeddedAsarIntegrityValidation on, OnlyLoadAppFromAsar on. Acompanhar os releases do Electron: a aba de advisories tem ~7 páginas só em 2026 (https://github.com/electron/electron/security/advisories).
- SEGREDOS. Tokens OAuth do Google e da Microsoft e chaves de API: guardar com Electron safeStorage (DPAPI no Windows) ou @napi-rs/keyring 2.1.2 (MIT, tem win32-x64/ia32/arm64, publicado 2026-10-19). NÃO usar keytar (7.9.0, último release em 2022-02-17). Segredo nunca entra em prompt nem em log; o modelo recebe só um identificador e o executor injeta o segredo (padrão 'proxy fora do sandbox' do Claude Code on the web). Escopos OAuth mínimos: ler antes de enviar; gmail.send só se pedido (OWASP LLM06 itens 4 e 5).
- AUDITORIA. Log append-only (SQLite cifrado) com: pedido do dono, plano, cada tool_use (args com segredos mascarados), decisão (regra, juiz, humano e o ID da regra), resultado resumido, origem e taint do contexto, versão e hash das descrições de ferramenta MCP. O goose registra cada decisão com 'finding ID'; o OpenHands e o LibreChat expõem trace e custo. Cobre OWASP ASI08 e o repúdio. Limitar ações por minuto e o custo por tarefa (OWASP LLM10).

O guia do OpenClaw cita uma arena de 2026 (272k ataques, 41 cenários): 0,5% Opus 4.5, 1,0% Sonnet 4.5, 1,3% Haiku 4.5, 8,5% Gemini 2.5 Pro, com resistência acompanhando a capacidade dentro da família. ## Custo estimado

Os componentes reaproveitados (sherpa-onnx, Silero, Smart Turn, openWakeWord, sandbox-runtime, MCP SDK, Stagehand/Playwright) não têm licença paga: US$ 0. O custo extra das camadas de segurança sugeridas, com preços já verificados pelo orquestrador (claude-haiku-5-5 a US$ 0,10/MTok de entrada e US$ 0,50/MTok de saída):
- Agente leitor sem ferramentas para conteúdo não confiável: 50 páginas ou e-mails por dia × ~8k tokens de entrada e ~500 de saída ≈ 0,4 MTok de entrada e 0,025 MTok de saída por dia ≈ US$ 0,05/dia ≈ US$ 1,50/mês.
- Juiz de ações de risco em Haiku: ~200 chamadas por dia × ~3k tokens de entrada e ~100 de saída ≈ 0,6 MTok de entrada e 0,02 MTok de saída ≈ US$ 0,07/dia ≈ US$ 2/mês.
- Extração e consolidação de memória em Haiku: ~30 conversas por dia × ~5k tokens ≈ US$ 0,02/dia ≈ US$ 0,60/mês.
Total das camadas: cerca de US$ 4 a 5/mês. Se o juiz rodar em claude-sonnet-5-5 (US$ 2/US$ 10), sobe para cerca de US$ 40/mês.
O custo principal (conversa no Opus 5.5, web search/fetch, computer use) é de outros domínios e não está incluído. O sandbox-runtime e a auditoria local não custam nada além de CPU e disco.

## Riscos

- Prompt injection indireta continua sem solução. Com as salvaguardas atuais a Anthropic mede 1,4% a 2,4% de sucesso de ataque adaptativo no navegador; o guia do OpenClaw cita mais de 80% contra defesas de ponta quando o atacante se adapta. Qualquer desenho que dependa só do modelo ou de classificador vai falhar algum dia.
- Fadiga de aprovação: confirmar tudo leva o dono a aprovar sem ler (OWASP ASI09/ASI10, 'Overwhelming Human in the Loop'). Exige sandbox e allowlist para reduzir prompts e confirmação forte só no que é irreversível.
- Áudio adversário: um vídeo ou página tocando no PC pode dizer 'trezentos, confirma' e acionar o agente. Wake word e confirmação por voz não são autenticação; ações de alto impacto precisam de confirmação na tela ou PIN.
- Envenenamento de memória de longo prazo (ASI06): um fato vindo da web vira 'preferência do dono' e influencia ações futuras. Mitigar com proveniência estrutural (OpenClaw), nunca só com filtro de conteúdo.
- Supply chain de MCP, skills e plugins: há casos reais de servidor MCP malicioso no npm (postmark-mcp, 09/2025; reverse shell, 10/2025), RCE no MCP Inspector (CVE-2025-49596) e no Figma MCP (CVE-2025-53967), e rug pull de descrição de ferramenta.
- O agente reescrevendo a própria configuração vira RCE persistente (família CVE-2025-53773, CVE-2025-54130, CVE-2025-59944, CVE-2025-61590). Proteger a pasta de configuração, a lista de MCP, os atalhos de inicialização e o registro.
- Ação destrutiva por mal-entendido, sem ataque: o Antigravity apagou o drive D: (12/2025); o Gemini CLI apagou um diretório (07/2025); o Replit apagou um banco de produção (07/2025). Exige lixeira, cópia e confirmação para exclusão.
- Dependências paradas ou com licença problemática: forks do nut-js sem release desde 2025, keytar desde 2022, @ui-tars/sdk desde 06/2025. Piper 1.x virou GPL-3.0; modelos pré-treinados do openWakeWord são não comerciais; o Agent SDK da Claude é proprietário.
- Hospedagem de modelos no Hugging Face (Smart Turn, turn detector do LiveKit, UI-TARS, classificadores de injeção) inacessível no build: exige mirror com hash ou download em runtime, o que cria um ponto de supply chain.
- Electron: ~7 páginas de advisories em 2026 (webview, sandbox de janelas, openExternal). Ficar mais de 2 a 3 versões atrás expõe o app; o UI-TARS (Electron 34) e o Goose (43) mostram como isso acontece na prática.
- sandbox-runtime no Windows é alpha (instalação elevada, Schannel quebra HTTPS, grants persistem) e pode não estar estável a tempo; o plano B é não expor shell genérico.
- Integrações Google/Microsoft com escopo amplo replicam o EchoLeak (CVE-2025-32711): um e-mail recebido injeta instruções e o agente vaza arquivos. Começar com escopos de leitura e marcar e-mail como conteúdo não confiável.
- Falsos positivos do wake word 'trezentos' (palavra comum em números falados em pt-BR: preços, notícias) podem acionar o assistente e enviar áudio para STT ou LLM na nuvem. É necessário treinar com muitos negativos numéricos e, opcionalmente, um verificador com a voz do dono.

## Verificação adversarial

Recomendação se mantém: **sim**

A recomendação principal se sustenta: núcleo próprio, reaproveitando padrões (contrato de eventos do HA, quadros do Pipecat, proveniência do OpenClaw, deny→ask→allow) e componentes permissivos. Quase todas as versões, datas e licenças conferem com npm, PyPI e os repositórios. Ela precisa de cinco correções antes de virar arquitetura.

(1) TTS pt-BR. O sherpa-onnx 2.0.0 removeu o espeak-ng. As vozes Piper pt_BR (phoneme_type espeak, voz pt-br) e o Kokoro agora exigem o fonemizador externo piper-phonemize-node, que é GPL-3.0-or-later, ou fixar o sherpa-onnx-node 1.13.8 (que também tem espeak-ng GPL). Para uso pessoal de um único usuário isso é aceitável, porque a GPL só cria obrigação na distribuição. Mesmo assim, a tabela de licenças e a open question sobre o espeak-ng precisam ser atualizadas, e o pacote GPL deve entrar explicitamente na lista de dependências.

(2) Node. O Electron 45.2.1 embute o Node v24.22.1. O 'Node 22' da stack é inconsistente: o alvo correto é o ABI do Electron 45 / Node 24, e o 'contra' do OpenClaw sobre Node 24 cai.

(3) Wake word. O openWakeWord declara suporte só a inglês, está sem release desde 02/2024 e tem licença ambígua para o embedding_model.onnx. As vozes Piper pt_BR são de 1 locutor cada. O plano 'trezentos' com cabeça própria continua válido, mas é experimental. Ele precisa de dados do próprio dono, de um verificador de 2º estágio com STT pt local do sherpa-onnx (modelo NeMo pt FastConformer em GitHub releases) e de comparação com o Porcupine, que suporta português (preço não verificado).

(4) Runtime ONNX. O Smart Turn e a cabeça do wake word exigem onnxruntime-node como segundo runtime ONNX, porque o sherpa-onnx não roda ONNX genérico. É preciso testar o conflito de DLLs no Windows.

(5) Segurança. O windows-install do sandbox-runtime dá, por padrão, leitura do perfil do usuário ao sandbox: usar --skip-profile-grant. O resumo do agente leitor continua 'untrusted' segundo o próprio OpenClaw, então o taint tem de persistir depois da quarentena. Os percentuais de ataque (1,4% a 2,4%) são de modelos 4.5 em 11/2025 e não medem os 5.5.

Ajustes menores: existe UIA em Node sem Python (@mediar-ai/terminator, MIT); a v1 do MCP SDK segue recebendo correções até cerca de 01/2027, então a troca para a v2 é certa mas não urgente, e falta checar a compatibilidade da v2 com servidores 2025-11-25; o Electron 43.4.0 do Goose está na faixa vulnerável do GHSA-9qh4-3jw8-366w, o que reforça a regra de acompanhar o Electron.

Limitações desta verificação: o orçamento de WebSearch estava esgotado, e picovoice.ai e learn.microsoft.com não resolvem nesta sessão. Para confirmar preço e plano grátis do Porcupine e os recursos agênticos do Windows 11, é preciso liberar esses domínios ou continuar numa próxima mensagem.
